# Network intrusion response runbook

Use this runbook to identify, triage, contain, and recover from network intrusion alerts generated by Cloud IDS or Next-Generation Firewalls in Stellar Engine environments on Google Cloud.

## 1. Runbook objective

This runbook guides security operators and incident responders through identifying, triaging, and containing network intrusion alerts from Cloud IDS and Next-Generation Firewalls across Stellar Engine landing zones on Google Cloud.

## 2. Audience and prerequisites

### 2.1 Target audience

- Tier 1, tier 2, and tier 3 Security Operations Center analysts
- Incident responders
- Network security engineers and platform teams

### 2.2 Responder prerequisites

- The `roles/logging.viewer` and `roles/securitycenter.viewer` roles for log analysis and scoping.
- The `roles/compute.networkViewer` role to trace IP addresses and inspect VPC topologies.
- The `roles/compute.orgFirewallPolicyAdmin` role via break-glass emergency access to add deny rules to hierarchical firewall policies such as `<prefix>-net-default`.
- The `roles/compute.securityAdmin` role via break-glass emergency access to apply Cloud Armor security policies, global or regional network firewall policies, or classic VPC firewall rules.
- Administrative access to third-party Next-Generation Firewall management consoles, such as Palo Alto Panorama, in deployments using virtual network appliances.

## 3. Operational scope

This runbook applies to all Stellar Engine environments, covering alerts from centralized inspection VPCs, Cloud IDS packet-mirroring endpoints, and Google Cloud networking logs across hub-and-spoke topologies.

Cloud IDS operates out of band through packet mirroring and only detects threats after traffic reaches its destination, whereas an in-path Next-Generation Firewall can block malicious traffic inline. Tailor containment speed based on which sensor generated the alert.

## 4. Identification and scoping

### 4.1 Detection sources

Monitor these telemetry sources for indicators of network intrusion:

- Cloud IDS alerts in Cloud Logging and Security Command Center reporting malware delivery, command-and-control beacons, or exploit attempts.
- Threat logs from centralized in-path Next-Generation Firewalls such as Palo Alto VM-Series or Fortinet FortiGate appliances.
- Event Threat Detection findings in Security Command Center derived from VPC Flow Logs, including `Cryptomining Domain DNS Request` and `Outbound connection to bad IP`.

### 4.2 Initial log assessment

1. Locate the intrusion alert entry in Logs Explorer scoped to the network host project where the Cloud IDS endpoint is deployed, such as `<prefix>-net-hub-host`, `<prefix>-net-vdss-host`, or the centralized `audit-logs` sink scope:
   ```text
   log_id("ids.googleapis.com/threat")
   ```
2. Record the network and signature fields from the `jsonPayload` object:
   - Record the `jsonPayload.source_ip_address` field for the originating IP address.
   - Record the `jsonPayload.destination_ip_address` field for the targeted IP address.
   - Record the `jsonPayload.name` and `jsonPayload.threat_id` fields for the matched CVE or malware signature.
   - Record the `jsonPayload.alert_severity` field assigned by Cloud IDS or the firewall sensor.
   - Record the `jsonPayload.ip_protocol` and `jsonPayload.destination_port` fields for the targeted transport protocol and destination port.

## 5. Triage and analysis

Verify whether the intrusion attempt succeeded, identify affected workloads, and establish the blast radius.

### 5.1 Alert verification

1. Research the matched `jsonPayload.name` and `jsonPayload.threat_id` signature fields to determine whether the traffic represents initial exploitation, lateral movement, or outbound exfiltration.
2. Check whether inline inspection blocked the traffic before it reached the target host:
   - Inspect the Next-Generation Firewall action field for `allow` versus `deny` outcomes, because a `deny` action confirms that the firewall blocked the packet inline.
   - Treat every Cloud IDS alert as delivered traffic and inspect the destination workload immediately because Cloud IDS mirrors packets out of band.
3. Correlate the source IP address against Shared VPC Flow Logs in the network host project to measure traffic volume and verify whether a sustained connection completed:
   ```text
   logName="projects/[NETWORK_HOST_PROJECT_ID]/logs/compute.googleapis.com%2Fvpc_flows"
   AND jsonPayload.connection.src_ip="[SOURCE_IP]"
   ```

### 5.2 Impact assessment

1. Map the source and destination IP addresses to specific Google Cloud resources, including Compute Engine instances, GKE nodes, and Cloud SQL instances.
2. Classify the traffic directionality to prioritize containment:
   - Classify traffic from external sources to internal targets as inbound scanning or exploitation against an exposed service.
   - Classify traffic from internal workloads to external destinations as high-priority outbound activity indicating potential host compromise, command-and-control beaconing, or data exfiltration.
   - Classify traffic between internal subnets or spoke VPCs as lateral movement across network segments.

## 6. Threat containment

Block malicious traffic, sever command-and-control channels, and isolate compromised internal hosts.

### 6.1 Immediate containment actions

1. Block malicious external source IP addresses and autonomous system numbers at the perimeter:
   - Add a deny rule to the Cloud Armor security policy when the attack targets HTTP or HTTPS workloads behind an external Application Load Balancer.
   - Add an emergency high-priority deny rule to the Networking folder hierarchical firewall policy `<prefix>-net-default` or to the global network firewall policy (`<prefix>-hub-fw-policy-0`, `<prefix>-<env>-fw-policy-0`, or `<prefix>-egress-fw-policy-0`) in `fast/stages-aw/2-networking-a-fedramp` deployments, or update the NGFW security profile and firewall policy rules in `fast/stages-aw/2-networking-b-il5-ngfw` deployments.
2. Execute the [IR-COMP-001](compute-resource-compromise.md) runbook immediately to quarantine the workload when outbound or lateral intrusion traffic originates from an internal virtual machine or GKE pod.
3. Push an emergency blocklist update or explicit deny rule to the centralized inspection appliances when operating in-path Palo Alto or Fortinet firewalls.

### 6.2 Terraform state alignment

- Apply emergency firewall and Cloud Armor blocks directly through `gcloud` or the Google Cloud console during an active SEV 1 response.
- Assign an engineer immediately to codify those emergency rules in the Stellar Engine Terraform repositories so the next CI/CD pipeline run preserves the blocks.

## 7. Eradication and recovery

Eliminate exploited workloads, remediate the targeted vulnerability, and confirm clean traffic flow.

### 7.1 Threat eradication

1. Destroy and redeploy any internal workload exploited during the intrusion rather than attempting in-place cleanup.
2. Patch the exploited application dependency or operating system package in source control before redeploying.
3. Add all newly identified attacker IP addresses and domains to permanent threat intelligence blocklists.

### 7.2 Traffic recovery

1. Confirm that legitimate application traffic flows normally and that emergency firewall rules did not block authorized clients.
2. Monitor Cloud IDS and Next-Generation Firewall logs for the matched `jsonPayload.name` signature and attacker IP ranges for 72 hours to detect evasion attempts.

## 8. Lessons learned

### 8.1 Post-incident review

1. Conduct a post-incident review within 5 business days with network, security, and workload teams.
2. Evaluate why the targeted port accepted traffic and determine whether the service belongs behind an internal load balancer rather than an external endpoint.
3. Tune Cloud IDS threat exceptions or firewall rules to suppress benign alerts from authorized vulnerability scanner IP addresses after confirming a false positive.
4. Update this runbook with any additional Logs Explorer queries or firewall commands used during the response.
